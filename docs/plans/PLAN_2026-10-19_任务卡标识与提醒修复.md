## 4. 阶段二：提醒送达核心（约一天）

### 4.1 补发窗口（修回归，最重要）
`api/reminders.ts` 的 `runCheck`：
```ts
const GRACE_MS = 12 * 60 * 60 * 1000   // 迟到 12 小时以内 → 补发；更早 → 只当历史，不炸屏
const late = now.getTime() - new Date(s.scheduledAt).getTime()
sent_at: late > GRACE_MS ? now.toISOString() : null
```
- 文案加"（补发）"：`reminderText(kind, title, date, time, { late })`，仅当 `late > 5 分钟`
- 新增单测：用例 A（晚扫描）必须 `sent=1`；超过 12 小时的历史仍不补发

### 4.2 通道级记账（替代单一 sent_at）
- 迁移 `supabase/migrations/018_reminder_channels.sql`
  ```sql
  alter table public.wb_reminders add column if not exists sent_channels jsonb not null default '{}'::jsonb;
  ```
- `sendDue`：逐通道记录 `{ webpush: true, telegram: false, telegramError: 'chat not found' }`；
  跳过已成功的通道；**所有已配置通道都成功**才写 `sent_at`
- 重试边界：**最终没有加 24 小时重试上限**。加了之后"通道坏了一周、修好后一次性补齐"会变成"静默丢弃"，
  而按通道记账已经把"重复消息"限制在失败的那个通道上；宁可贵一点，也不再把消息悄悄扔掉（这正是本轮要修的毛病）。

### 4.3 客户端定时器（应用开着时"准时"）
- `src/modules/reminders/api.ts`：新增 `useReminderTimer()`
  - 取最近一条未到期的 `scheduledAt`，`setTimeout` 到点 → `invalidateQueries(['reminders'])`
  - 页面不可见时不清定时器，但最长 24 小时后重排一次
- `layout.tsx` 挂在 `useReminderSync()` 旁

### 4.4 可观测（把"静默失败"变成"看得见"）
- `/api/reminders?entry=test` 返回逐通道结果 `{ telegram: {ok, error}, serverchan: {...}, webpush: {...} }`
- 设置页「测试发送」按结果逐行显示（失败带服务端原文）
- `/api/check-reminders` 返回 `scannedAt`，提醒中心页脚显示"上次扫描：N 分钟前"

## 7. 风险与回滚

| 风险 | 处置 |
|---|---|
| 补发窗口开太大 → 历史提醒集中炸出 | 12 小时窗口 + 单次最多 20 条上限；超限只发汇总 |
| 迁移 018 写错 | 只加列、默认值安全；回滚 SQL 写在文件头 |
| 通道重试造成重复消息 | 按通道记账，成功的通道不再发 |
| 卡片改版影响 e2e 选择器 | e2e 断言限定在 `[data-flip-id]` 作用域，不用颜色类名 |
