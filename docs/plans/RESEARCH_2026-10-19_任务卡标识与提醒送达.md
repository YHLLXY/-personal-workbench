### 0.2 Telegram 到点不提醒：v1.31 的一处回归 + 一个长期存在的调度短板

**直接原因（回归）**：`api/reminders.ts:203-211` 新建提醒时，只要 `scheduled_at <= now` 就直接把 `sent_at` 写成当前时刻（注释写着「不补发」）：

```ts
sent_at: new Date(s.scheduledAt).getTime() <= now.getTime() ? now.toISOString() : null,
```

于是**第一次扫描发生在到期之后**的那条提醒，永远不会进入 `sendDue()` 的查询（`sent_at is null`），外部通道（Telegram / Server酱 / Web Push）一条都不会发。而应用内横幅只看 `scheduledAt` 是否到期，照常显示 —— **这正是"内部提醒器有反应、手机没消息"的形状**。

v1.31 之前（`1e73c4f9^`）新建行不带 `sent_at`，同样的场景会正常发出。回归发生在 2026-10-16 22:11 的那次部署。

**系统性原因**：唯一能"到点主动发"的服务端触发器是 GitHub Actions 的 `*/20` cron。实测（见 §1.2）：中位间隔 **199 分钟**、最长 **410 分钟**、没有一个间隔 ≤ 60 分钟。

**放大器**：`sent_at` 是**整行一个字段**，任意通道成功即视为已发送（`api/reminders.ts:338`），其他通道当次失败就再无补发机会（§1.3 用例 C 已复现）。

### 1.3 本地复现（内存 Supabase fake，跑的是生产同一份 `api/reminders.ts`）

场景：任务「交报告」，上海 14:00 到期（`scheduled_at = 06:00Z`），已配置 Telegram。

| 用例 | 条件 | 结果（实测输出） |
|---|---|---|
| **A** | 第一次扫描在 14:10 | `created=1, due=1, sent=0`，Telegram 调用 **0** 次，行被写成 `sent_at=06:10Z` |
| **B** | 13:50 扫过一次，14:05 再扫 | 第一次 `created=1, sent=0`；第二次 `sent=1`，Telegram 调用 1 次 |
| **C** | Web Push 成功 + Telegram 失败（chat not found），20 分钟后再扫 | 第一次 `sent=1, skipped=1`（push 成功掩盖 TG 失败）；第二次 **不再重试**，`sent_at` 已落 |
| **D** | 库里 `scheduled_at = "...07:00:00+00:00"`，代码算的是 `"...07:00:00.000Z"` | 每次扫描都判定为「改期」→ `updated=1` |

用例 A 就是线上那条路径：**建任务晚于上一次扫描、到期又早于下一次扫描 → 外部通道永久静默，应用内照常显示**。

## 2. 调研：提醒调度（怎么保证"到点"）

| 方案 | 精度 | 成本 | 判断 |
|---|---|---|---|
| GitHub Actions `schedule`（现状） | 实测中位 3.3 小时 | 免费 | **只能当兜底**，不能当主触发器 |
| Vercel Cron | Hobby：**每天 1 次**、按小时精度；Pro：每分钟 | Hobby 不可用；Pro $20/月 | 个人项目不值得 |
| Supabase `pg_cron` + `pg_net` | 分钟级，库内定时直接发 HTTP | 需确认实例是否启用扩展（**待验证**） | 架构上最省心：不依赖外部 tick |
| 第三方 ping（cron-job.org / UptimeRobot 等） | 1–5 分钟 | 免费额度 | 最省事，代价是多一个外部账号；国内可达性需实测（**待验证**） |
| 客户端定时器 | 精确，但只在页面开着时 | 0 | 必须做（应用开着时体验才对） |

成熟产品的做法（产品观察，非逐条引用）：提醒类产品普遍把"**错过补发**"当成一等公民 —— 系统休眠/离线后恢复时，会把错过的提醒以"（补发）"或"逾期"形态发出，而不是静默丢弃；同时应用内与推送共享同一份"已投递"记录，避免一边有一边没有。

**我们的取舍**：短期靠"客户端定时器 + 第三方 ping（或 pg_cron）"补精度，GitHub cron 降级为兜底；语义上把"过期多久还算该补发"做成一个有上限的窗口，而不是一刀切。

## 3. 调研：优先级标识（不用整卡染色还能怎么标）

WCAG 2.2 **1.4.1 Use of Color**（§6 参考 3）原文要求：*"Use information in addition to color, such as shape or text, to convey meaning."* —— 颜色可以当加速器，不能当唯一载体。

产品观察（同类工具的实际做法）：

| 产品 | 标识法 | 是否整卡染色 |
|---|---|---|
| Todoist | P1–P4 彩色旗标图标 | 否 |
| TickTick | 彩色旗标 + 列表色 | 否（列表视图有左侧色条） |
| Apple 提醒事项 | 优先级 = `!` / `!!` / `!!!` | 否 |
| Microsoft To Do | 重要 = 星标 | 否 |
| Linear / GitHub | 优先级图标、彩色左轨 | 否（左轨是列表项的经典做法） |

结论：**整卡淡染不是行业惯例，左侧轨道 / 图标徽章才是**。结合我们已有的"焦点金边"，轨道方案可以同时容纳"紧急度（颜色）"和"焦点（边框）"两个维度，且完成后轨道可以保留。

## 4. 取舍

| 决策点 | 选择 | 理由 |
|---|---|---|
| 卡片标识 | 左侧 3px 状态轨 + 中性底色 | 与白卡有确定的形变差异，不依赖 1.2:1 的色差；轨道在深色模式同样成立 |
| 是否加文字徽章 | 先不加（方案 C 备用） | 每张卡多一个元素会吵；颜色冗余由已有的优先级圆点 + 轨道形状承担 |
| 完成态 | 保留轨道（35% 不透明度）+ 标题划线 + 底色转 muted | 「这件事原来多紧急」还在，只是褪色，符合直觉 |
| 提醒补发 | 用时间窗（建议 12 小时）判定"该不该补发"，取代"一律不补发" | 既能覆盖"扫描稀疏导致的迟到"，又不会把几个月的历史一次炸出来 |
| 通道记账 | 每通道独立记录（需迁移 018） | 单 `sent_at` 会被任一通道成功掩盖（用例 C） |
