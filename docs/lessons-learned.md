## 2026-11-16 · 返回键关不掉浮层 + 提醒重复弹（v1.33.1）

**一句话**：两个 bug 是同一个母题——**只活在内存里的状态，既没人替你关掉，也记不住自己做过什么**。

### 1. 「快速捕获退不出来」不是关不掉，是根本没在关

- **症状**：手机上打开快速捕获，按返回键，界面「反复横跳」退不出来。
- **复现**（Playwright + Chromium 手机视口）：`/` → 底部 Tab「学习管理」→「工作台总览」→ 打开浮层 → `goBack()`：
  URL 退回 `/study`、浮层仍然盖着。再按一次返回 → 又跳回 `/`。**这就是「反复横跳」的实物**。
- **根因**：浮层只是 zustand 里的一个布尔值，**从没进过浏览器历史**。返回键弹掉的是**浮层背后的路由**。
- **修法**：`src/app/use-overlay-back.ts` —— 浮层打开时 push 一条**同 URL** 的记录；`popstate` 关浮层；
  手动关（X / 遮罩 / Esc）时把这条记录弹掉，历史里不留「按返回没反应」的死记录。
  两个必须处理的细节：① 命令面板点「新建任务」是**同一 tick 里关面板 + 开浮层**，cleanup 里的 `back()`
  必须推迟到微任务并按 token 跳过，否则新浮层会被自己的 back 弹掉（面板一闪就关）；
  ② 由 `popstate` 关闭时 cleanup 必须跳过 `back()`，否则会多退一步。
- **教训**：自绘浮层（不是 `<dialog>` / base-ui Dialog）都要先问一句「返回键按下去，它凭什么关？」

### 2. 提醒「发多次」：去重账本活不过一次挂载

- **症状**：同一个任务的提醒弹了多次。
- **根因**：横幅的 `notifiedRef` 是 `useRef` —— 离开首页再回来就是全新挂载、账本清零。
  而「要不要弹」只看 `sentAt`，它由服务端在**所有已配置通道都成功**时才写：
  任一通道失败（如 Telegram 没配对）或一个通道都没配，`sentAt` 永远是 null → 每次回首页都再弹一次。
- **修法**：`src/modules/reminders/notify-log.ts`，账本落 localStorage，键 = `id@计划时刻`
  （改期算一条新提醒、应该再提醒），7 天过期。
- **教训**：**去重状态的生命周期必须 ≥ 它要去重的事件的生命周期**。挂在组件上的去重，等于每换一页就忘一次。
- 附带：服务端写 `sent_at` 的那条 update **不检查 `error`** —— 缺列（例如迁移 018 没执行）时更新静默失败、
  `sent_at` 永远为空 → 每轮扫描把同一批提醒重发。现在失败会进函数日志。

### 3. 「迟到」不是 bug，是架构

- 应用退到后台后页面被系统挂起（Android 冻结/节流、iOS 直接挂起），`useReminderTimer` 的 `setTimeout` 不可能准点。
  后台送达只能靠**服务端定时扫描**。
- 精度 = cron 间隔 + 推送通道延迟：Supabase pg_cron（`supabase/cron/reminders-5m.sql`，5 分钟）
  > GitHub Actions（实测中位 **199 分钟**）。
- 要更准只能把 pg_cron 调密；「到底有没有在跑」用该文件末尾的三条自检 SQL 确认（200/401/timed_out 各有含义）。

### 4. 体积门禁降级为「烟雾报警器」（2026-11-16 用户拍板）

- **症状**：基线总量 **1149.4 KB / 预算 1150 KB** —— 只剩 1 KB，任何一次修复都会红。
- **诊断**：这个数把三样不同的东西混在一起——vendored 依赖（supabase 267 KB，其中 realtime/storage 一行没用）、
  纯数据（changelog 42 KB 中文）、业务代码；而且量的是**未压缩**字节，还把**懒加载 chunk** 也算进去。
  实测：全站 1151 KB = **brotli 324 KB**；首屏 726 KB = **192 KB**；入口 306 KB = **83 KB**（每次发版只重下这一块，
  因为 SW 预缓存了全部 56 个 chunk）。
- **纠错**：中途我提过「把 supabase-js 拆出首屏」，被用户追问后自己推翻了——它对**总量**一分不减（卡我们的正是总量），
  对已安装 PWA 收益≈0（chunk 早已在缓存里），还可能因为失去 `modulepreload` 让首屏**更慢**。
  **拿 bundle 数字当体验证据，是这次差点犯的错。**
- **决定**：`check-bundle.mjs` 从「预算门禁」降级为「体检」——只拦灾难线（首屏 brotli > 400 KB /
  总量 > 2500 KB / 单 chunk > 800 KB），正常加功能不红；每次构建打印真实数字（含 brotli）。
  AGENTS/README 的「体积红线神圣不可侵犯」同步改写为「体积只盯关键路径」。
- **连带放开**：依赖取舍回到准则 #5/#6 —— 只有**会进入口 chunk** 的库才掂量体积，懒加载页面里的成熟库（dnd-kit/rrule 之类）随便用。
- **保留的那条仍是真红线**：首屏（brotli）。它守的正是 recharts 那类「把大库塞进壳层」的事故。

### 待办 / 风险

- `sendDue` 仍是「select → 发 → update」，两个扫描并发时会重复推送（**没有原子认领**）。
  真出现「随机重复」，下一步应加 `claimed_at` 列做 CAS（迁移 019）。
- `tests/review-real-gateways.test.ts` 读的是**知识库里的真实门户口**：`天翼AI杯` 的 `phase: 已提交`
  不在允许的四态里 → 全量测试有 1 条红，与代码无关（环境数据，需用户决定改笔记还是放宽状态机）。

## 2026-10-16 · AI 日报上线七个缺陷（v1.28.4 → v1.30.3）

**背景**：AI 日报代码写完、601 个用例全绿、构建与体积门禁通过、迁移也执行了，
**但线上第一次运行就 500，一次都没成功过**。一天内连挖七个缺陷。

### 项目相关的具体根因

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | enrich 稳定 500 | 迁移 015 的 CHECK 漏了 `processing`，而 `wb_claim_items()` 正是写这个值 | 迁移 016 重建约束 |
| 2 | 错误只有 `internal error` | PostgREST 报错是普通对象，被 `instanceof Error` 吞掉 | `errText()` 摊平 + `stage` 标签 |
| 3 | build 报「无法解析」 | `deepseek-flash` 思考 token 计入 `max_tokens`，2000 里吃掉 1925 | 默认发 `thinking: disabled`；截断当场抛错 |
| 4 | 「立即生成」报 22P02 | `persistSession:false` 的客户端 `getUser()` 返回 null，`?? ''` 把空串当 uuid | `authUser` 连 `userId` 一起返回 |
| 5 | 生成了但 App 看不到 | 服务端按「库里第一个用户」写日报，**库里有 2 个用户** | 配 `DIGEST_USER_ID`；自检报出用户总数 |
| 6 | 日报「信息太少」 | 编排发给模型的只有 `{eventId,title,category}`，**已生成的摘要一个字没传** | payload 带上 summary；科技配额 4→12 |
| 7 | 处理不完就顺延 | 时间预算按**总量**切，抓取的 11 秒吃掉了摘要的份额 | 改按**剩余**时间 60/40 拆 |

### 项目专属的工程约定（后续迭代遵守）

- **`api/*.ts` 单文件约束**：`telegramGetMe` 这类小工具宁可复制一份，也不能跨文件 import。
- **迁移必须由用户在场执行**，agent 只写文件。写迁移时**建表语句与同一个文件里的函数要对得上**
  （缺陷 1 就是这么来的）。
- **时间预算要区分「固定开销」与「可变开销」**：`/api/hot` 抓 25 个源实测约 11 秒，
  是固定开销，不该从模型份额里扣。
- **服务端替用户猜身份的地方（目前只有 `resolveUserId`）必须让猜测可见**：
  自检报总数与来源，接口响应带 `user` 前 8 位。
- **专属环境变量速查**：`DIGEST_USER_ID`（归属账号，**多用户时必须配**）、`DIGEST_BUDGET_MS`（50000）、
  `DIGEST_FOCUS_CATEGORY`（科技）/`DIGEST_FOCUS_PER_CATEGORY`（12）、`DIGEST_PER_CATEGORY`（4）、
  `LLM_THINKING`（默认关思考）。

  真紧了应把 changelog 改成按需 fetch 的 JSON，**不要删历史条目**。

## 2026-10-16 · 月亮数据线 + 提醒派生重构 + 任务状态语义（v1.31.0）

**一句话**：三件事撞在同一个母题上——**把「派生数据」当成「独立实体」来维护**。

### 做了什么

| 需求 | 判断 | 改动 |
|---|---|---|
| 「太阳的起落线做好了，为什么月亮的不做」 | Open-Meteo 没有任何月亮字段，免费月亮接口都要 key + 配额 | 新增零依赖 `src/lib/moon.ts`（Meeus 截断级数）+ 天气弹窗「月出月落」一节 |
| 「提醒里为什么还有留存？还可以恢复？是不是设计缺陷」 | 是。提醒是任务/考试/目标的**派生视图**，却被做成了带独立生命周期的实体 | 删掉 `dismissedAt` 与整套「忽略 / 恢复 / 全部忽略 / 已忽略筛选」；服务端改增改删三向对齐 |
| 「紧急程度变底色、焦点加金星金边、进行中与将来到底是什么逻辑」 | `doing` 不影响任何过滤（日期不是今天就在今日页看不见）；`someday` 与日期、重复规则互相打架 | 三态语义补完 + 卡片配色 + 焦点金框 + `focusDate` 复活修复 |

### 关键决策与理由

1. **月亮自己算，但不由自己说了算**：否决 `suncalc` 运行时依赖（11 KB 吃掉 JS 总量余量的**一半**），改手写；
   同时把它装成 **devDependency 只做测试裁判**——365 天 × 中低纬 3 站逐点比对（重庆全年最大偏差 **0.73 分钟**），
   外加日食/月食这类**与任何实现无关**的真值锚。**运行时零依赖、测试时双实现互证**，本项目第一次用这个模式。
2. **逾期口径必须全站唯一**：提醒红底若按「时刻」判，同一个任务会在「今日待办」不红、「提醒中心」红。
   统一按**日期级**（`dueDate < today`），与既有 `overdueTasks` 同尺，理由写死在纯函数注释里。
3. **新建已过期的节点不补发**：否则首次接云端、撤销完成、从「将来」转回来，都会把几十条历史提醒一次性炸出来。
   规则：`scheduled_at <= now` 的新行直接写 `sent_at = now`。**「改期到未来」才重置投递**，改期到过去保留投递记录。
4. **`doing` 纳入今日区**，而不是删掉这个状态：它现在有唯一且可解释的含义（正在推进、要天天看到），
   并且**有出口**（卡片胶囊点一下回普通待办）——旧版只能在编辑弹窗里改，等于没有出口。
5. **删 `dismissed_at` 列必须用户在场**：迁移 `017` 只做 `drop column if exists`，代码不依赖它，
   **先部署再执行**，回滚 SQL 写在文件头。

### 验证

- `npm test` **653 passed / 70 files**（新增 `tests/moon.test.ts` 10 例；reminders 四件套 + 仓储三件套全部改写）
- `npm run build` 通过；`check:bundle` **首屏 724/790 · 总量 1141/1150（本轮 +12 KB）· 最大 chunk 304/340**
- `npm run lint` **11 警告 ≤ 基线 12**（中途出现过 13：新测试里的 `mock.lastCall?.[0]` 触发
  `no-unsafe-optional-chaining`，改成显式取值函数后回落）
- E2E 冒烟 + 真机截图：见文末交付记录

### 反向教训（这一轮最容易再犯的）

- **门禁文件注释里的基线数字会过期**：`check-bundle.mjs` 注释写着 1103 KB（2026-10-15 定基时的数），
  动手前实测已是 **1129 KB**（上一轮日报工作涨的）。**引用前先实测，别把注释当事实。**
- **删一个状态之前，先问「它的出口是什么」**：提醒的「忽略」不是功能，是**没有出口的补丁**；
  真正该给用户的是「处理掉这件事」。
- **别在测试里用 `?.` 取 mock 调用**：`oxlint` 的 `no-unsafe-optional-chaining` 会算进警告基线。
- **行尾符不统一会让脚本改动翻车**：同一仓库里既有 LF 也有 CRLF 文件，多行锚点替换必须先归一化行尾
  （本次在 `task-dialog.tsx` 上因此写坏过一段 JSX，靠 `tsc` 才抓到）。

### 遗留 / 用户侧

- ⚠️ **体积余量只剩 9 KB**（1141/1150）——**这是当前最紧的一条红线**。真到顶了应把 changelog（34 KB chunk）
  改成按需 fetch 的 JSON，**不要删历史条目**。
- 迁移 `017_drop_reminder_dismissed.sql` **待你在 Supabase 执行**（顺序：先部署新版本，再执行）。
- 月亮模块在 |纬度| ≥ 60° 的「擦边日」会与 oracle 差到小时级（那里月亮可能连续 23 小时不落，高度曲线近乎相切，
  两种扫描法对「哪一次算月出」本就没有共识）。本应用只渲染重庆，精度已按纬度分档写进 `tests/moon.test.ts` 顶部。

## 2026-10-19 · 提醒「内部有、手机没有」+ 卡片底色读不出来（v1.32.0）

**一句话**：两个问题都不是"没实现"，而是**实现看起来对、测试也是绿的，但真实使用路径没被任何断言覆盖**。

### A. Telegram 到点不提醒

| 现象 | 根因 | 证据 |
|---|---|---|
| 应用内横幅照常显示，手机一条收不到 | v1.31 的"防炸屏"规则：新建提醒时只要 `scheduled_at <= now` 就写 `sent_at = now`。于是**第一次扫描发生在到期之后**的提醒永远进不了发送队列 | 内存 fake 复现：`created=1, due=1, sent=0`，Telegram 调用 0 次；而横幅只看 `scheduledAt` 是否到期 |
| 就算没有这条规则，也会晚 1~7 小时 | 唯一的主触发器是 GitHub `*/20`，实测 25 次运行中位间隔 **199 分钟**、最长 **410 分钟**、≤60 分钟的 **0** 次 | GitHub Actions API 全量 runs；官方文档也写明 schedule 会延迟、可能被丢弃 |
| 一个通道成功就把整行标成"已发送" | `sent_at` 是整行单字段，Web Push 成功（FCM 201 但设备收不到）会永久掩盖 Telegram 的失败 | 复现：push 成功 + TG 失败 → `sent_at` 已写；下一轮不再重试 |

**为什么测试没发现**：`tests/reminders-api.test.ts` 里有一条**断言这个行为**的用例
（"新建已经过期的提醒 → 直接标记已发送"），用的是 2026-01-01 的老日期，正好落在"历史"区间；
而"迟到 5 分钟的当天任务"这条真实路径，谁也没测。

**修法**：12 小时补发窗口（迟到仍发、文案标"（补发）"）+ 通道级记账（迁移 018）+ 页面开着时到点自触发 + 逐通道测试结果回显。

### B. 任务卡底板"太淡"，完成态颜色"直接消失"

- 实测：`bg-destructive/8` 合成后与白卡对比 **1.18:1**，`bg-accent/12` **1.13:1**，深色模式 **1.006:1**。不是"淡"，是**读不出来**。
- 完成态一次性切换 `opacity-60 + bg-muted/40 + 去掉底色`，所以"颜色瞬间消失"是代码直译，不是动画丢了。
- 修法：左侧 3px 状态轨（高红 / 中 `#A98F55` / 低不画）+ 完成态轨道留 40%；"中"档为拿 3:1 对比专门调深（`--priority`）。

### 沉淀成规则

1. **"测试绿"不等于"路径对"**：凡是断言里写死了某个绝对日期，就要问一句「这个日期落在哪个分支」。
   断言一个 buggy 行为比没有断言更危险——它会把 bug 钉死。
2. **送达语义必须按通道记账**：单一 `sent_at` 在"某通道静默失败"时必然丢消息，而 Web Push 在中国大陆正是这种通道。
3. **定时器精度要实测，不要信 cron 表达式**：`*/20` 在 GitHub 上是小时级；README 里的数必须是实测中位数，不是设计意图。
4. **颜色编码必须过 3:1 这一关**（WCAG 1.4.11 非文本对比）：3px 轨道低于 3:1 等于没画；整卡 8% 透明度天然不可能达标。
5. **"完成后保留标识"是语义问题不是审美问题**：紧急度是这件事的属性，完成不改变它曾经多急。

### C. PC 首页的「大空洞」和更新日志的滚动条（同日追加）

- **空洞不是"列跨度没对齐"，是行高**：12 列网格按行排，一行的高度由最高的卡决定，矮卡底下必然是空白。
  v1.26 只修了「每行凑满 12 列」，行内高度差造成的空洞一个都没动——所以用户看到的"还是有很多空隙"一直存在。
  改成 CSS 多列瀑布流（`columns-2 / xl:columns-3`）后，列内不再共享行高；浏览器实测相邻卡间距最大 **16px**（= 设计间距）。
- **顺手踩到的坑**：把 `md:grid` 换成 `md:columns-2` 时忘了 `display` 是另一回事——容器留着 `hidden`，
  整面卡片墙直接不渲染（量出来 11 张卡、3 列变成 1 列、maxGap=0）。**换布局工具类时先确认 display 有没有人管**。
- **更新日志不该塞进弹窗**：448px 宽 + `max-h-[80vh] overflow-y-auto` 的组合在 PC 上又窄又挤出横向滚动条
  （`overflow-y:auto` 会把 `overflow-x` 也变成 auto）。内容是给人"读"的，就给一整页；弹窗只留最新一版当引子。
- **文案里的 `**…**` 从来没人渲染**：三处展示都原样吐星号。用了 10 行的 `RichText` 解决——
  为一种语法引一个 markdown 解析器，在只剩 3KB 余量的包里不划算。

### 遗留 / 用户侧

- 迁移 `018_reminder_channels.sql` **待你在 Supabase 执行**（顺序：**先 018，再部署** v1.32 —— 缺列会让 cron 500）。
- 主触发器改用 **Supabase Cron（pg_cron + pg_net）**：不用新账号，SQL 见 `supabase/cron/reminders-5m.sql`。
  （教训：上一版建议的第三方 ping 服务用户根本注册不上，方案卡了一次；这次先确认「用户能不能用」再写进方案。）

### D. 「行高」修完了，「列高」还是洞（2026-10-20）

- v1.32 修的是**行内高度**（一行里矮卡不被拉高），可三列各自独立堆叠之后，**列与列之间的高度差**没人管：
  实测 707 / 860 / 860，左列下方 153px 空白。用户一句「还是有很大的空隙」把问题指回原点。
- 结论：瀑布流只保证「列内没有洞」；**页面级空洞要靠「分列配平」或「按行对齐」来消灭**。
  最终选 12 列 Bento：同行等高（`items-stretch`），多出来的高度落进卡片内部（`CardContent` 设 `flex:1`）。
  实测行内高度差 0px、垂直间距处处 16px（1440 / 1920 / 1280 / 768）。
- **`grid` 容器里的 `flex-row` 是个哑巴**：`CardHeader` 是 grid，各处写的 `flex-row items-center justify-between`
  只改 `flex-direction`、不改 `display`，第二项（定位 / 条目数 / 箭头）一直被排到下一行，卡片凭空高 20px。
  改成 `flex items-center justify-between` 才真是一行。**改布局类之前先看 computed display。**
- **`truncate` 必须配 `min-w-0`**：flex 子项默认 `min-width:auto` = 不换行文本的宽度，它会顶宽父容器；
  而 `overflow-y:auto` 会把 `overflow-x` 一起变成 auto —— 于是「省略号」变成「被切掉 + 横向滚动条」。
- 量尺寸要用脚本，不靠肉眼：一次跑完 1440/1920/1280/768/390 + 浅色深色 + 弹窗宽度，输出每行卡片高度与垂直间距。

## 2026-11-17 · v1.34：提醒的「唯一投影」与其它五处（A–F）

**一句话**：这轮六个问题里有四个是同一个毛病——**同一份事实在多个地方各算一套**；剩下两个是
「用户做了动作，界面没给回声」。

### 1. 提醒行不是独立数据，是任务的投影（图一/图二）

- **症状**：提醒中心点「完成」，卡片赖着不走；任务把提醒时间清空后，卡片没了、**手机照响**。
- **根因**（两条，缺一不可）：① 前端 rows 直接来自 /api/check-reminders，完成只 invalidate 了
  taskKeys，没有任何一层把它和任务对齐 —— 观感是「点了没反应」；② 服务端 liveRefKeys 判任务存活
  **只看 status**，而 computeReminders 生成节点要求 **dueDate + dueTime 都有** —— 用户清空时间后
  那行永远不删，到点照推。**只修前端等于把「卡片赖着不走」换成「卡片没了、手机照响」。**
- **修法**：effectiveRows(reminders, sources, { today }) 成为**唯一投影**——task 行的 scheduledAt
  用任务现算（改期立刻生效）、已完成/已删除/无提醒时间的行不出现；exam/goal 原样透传。
  提醒中心、侧边栏角标、首页横幅全部读 useReminderView()，否则就是 v1.31 修过的「角标 3 条、列表 2 条」复发。
- **教训**：**派生数据必须只有一个计算入口**。一旦第二个消费者（角标）自己 map 一遍，
  两边就一定会漂移——不是"可能"，是"迟早"。
- 附带代价：layout 里的角标现在会顺带拉 tasks/exams/goals 三个查询（原来只有 reminders）。
  这是"单一投影"的必付成本，比两个数字对不上便宜。

### 2. 第二个「完成」按钮写死 status=done，会终结整条重复序列

- 提醒中心的完成按钮是 update({status:'done'})。对普通任务是「完成」，对每日任务就是**把序列删了**
  —— 第二天它不会再出现，而用户看不出发生了什么。
- **修法**：src/lib/task-rules.ts 的 completionPatch(t, today) 把「重复任务滚到下一期 / 普通任务标记完成」
  抽成纯函数，返回 { patch, undo, nextDue? }；两个入口共用。顺带让撤销变精确（还原完成前的原
  dueDate / 原 status，不再用 prevOccurrence 倒推）。
- **教训**：**同一个动作有多个入口时，规则必须先抽出来**。写在组件里的规则，第二个入口一定会走偏。

### 3. 「刷新」没有回音：一半是真没变，一半是文案在说谎

- 服务端 s-maxage=600 + 客户端 staleTime 10min，点刷新绝大多数时候数据**确实没变**；
  而 loadProjects 在接口失败时**静默回退静态快照并当成功返回**，所以「刷新失败」这条文案几乎不可达。
- **修法**：文案按**接口自带的 updatedAt**（服务端生成时刻）分三种，三种都可达；
  **不能用 dataUpdatedAt** —— 那是客户端收到的时刻，CDN 给 10 分钟前的副本时它照样显示当前时间。
  用常驻状态行（role=status + aria-live）而不是 toast：toast 几秒就没了，「生成于 HH:mm」留不住。
- **教训**：**「没有变化」也要说出来**，而且要说出"谁没变、什么时候生成的"，否则用户以为按钮坏了。

### 4. 明日待办：用户没看见 = 没生效

- 生成到「明天」的条目在「今日待办」里根本不会出现，旧实现只弹一句 toast → 用户以为没生效。
- **修法**：两段式——可编辑预览（勾选 + 改字）→ 确认 → **就地列出生成结果** + 「去待办查看」。
  去重只对「同一天已存在」的任务生效（existingTitles），重复生成会明说「跳过 N 条（已存在）」。
- **实施偏差（记录）**：计划表格里写了「parsePlan 增加去重」，但同一节的决定 ③ 明确说
  「批内保留，一天两次背单词是合法用法」——两者冲突。**按决定 ③ 实现**：parsePlan 不去重，
  误重复交给可编辑预览兜（用户能看见、能取消勾选）。文件表格那句是笔误。
- 另一处偏差：B 段验收写「出现 toast」，实际用常驻状态行 + aria-live。理由同上（toast 留不住时刻），
  文案三条与验收要求完全一致。

### 5. 动效：克制不是"少做"，是"只有一套节奏"

- 页面 300ms、卡片 400ms、勾选 300ms 带回弹——三套时长各自为政，看起来就是"东一下西一下"。
- 收敛成 --dur-fast/base/slow + 一条 --ease-out-soft（140/180/200ms），勾选不再回弹超过 1.0；
  prefers-reduced-motion 一次性关掉全部入场；「回到顶部」在减轻动效时**直接跳**
  （JS 的 scrollTo smooth 不吃 CSS 媒体查询，必须自己判断）。
- **教训**：动效的"统一感"来自**时长与缓动被集中定义**，不是来自每个动画都做得更精致。

### 6. Server酱³：换端点不换通道 id

- wb_channel_configs.serverchan_key 复用，key 形态（sctp…）决定端点，**不新增 channel id**：
  sent_channels 按通道记账，新增一个 id 会让同一行按两个通道各发一次。
- SC3 的响应要连**服务端原文**一起回显：只认 {code:0} 时，响应形状一变就只剩一句"失败"，线上无从判断。
- **教训**：**记账键是契约**。给一条链路换实现时，先确认"谁用它记账"，再动 id。
